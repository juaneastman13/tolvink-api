================================================================================

1.1 ARQUITECTURA GENERAL

El módulo WhatsApp está compuesto por 4 providers y 1 controller (src/whatsapp/whatsapp.module.ts):

  • WhatsAppController (whatsapp.controller.ts, ~809 líneas)
    Expone los endpoints HTTP. NO está protegido con JWT: la autenticación descansa
    en HMAC-SHA256 (firma Meta) y tokens firmados (verifySignedToken).

  • WhatsAppService (whatsapp.service.ts, ~793 líneas)
    Wrapper de Meta Cloud API v22.0: sendText, sendButtons, sendList, sendSelection,
    sendTemplate, markRead, sendTypingIndicator, downloadMedia (con whitelist SSRF:
    lookaside.fbsbx.com, scontent.whatsapp.net, media.fna.whatsapp.net),
    uploadToStorage (bucket "freight-docs" en Supabase). Retry con backoff [1s, 3s, 9s].
    Crons de limpieza cada 30 min. Crons de recordatorios y resumen diario DESACTIVADOS
    (comentados en onModuleInit líneas 63-69 — fase testing).

  • WhatsAppRouterService (whatsapp-router.service.ts, ~3102 líneas)
    Orquestador principal. Rate limit por teléfono (30 msg/min in-memory + 45 msg/min DB),
    phone lock secuencial (phoneLocks Map, cap 10.000), dedupe de mensajes con PG advisory
    lock, cooldown para "no registrado" (10 min) y GPS (30 s).

  • WhatsAppFlowService (whatsapp-flow.service.ts, ~325 líneas)
    Gestiona flujos multi-step (reject, confirm_loaded, cancel_freight). Timeout 10 min.
    Rate limit 30 mensajes por flujo en 5 min.

  • AgentService (src/ai/agent.service.ts, ~419 líneas)
    Agente IA (Gemini) con tool-loop (MAX_TOOL_ITERATIONS=15, TOOL_TIMEOUT_MS=120s,
    MAX_HISTORY_MESSAGES=40, SESSION_TIMEOUT_MS=60 min, PROMPT_CACHE_TTL_MS=5 min).
    Layer deterministic intent antes de llamar al LLM.

1.2 MODELO DE IA

  • Provider:      Gemini (@google/genai), configurado en GeminiClient (src/ai/core/gemini.client.ts)
  • Modelo:        configurable via GEMINI_MODEL env
  • Audio:         OpenAI Whisper (whisper-1) via OPENAI_API_KEY
  • System prompt: buildSystemPrompt (src/ai/core/prompt-builder.ts)
  • Cache key:     ${sessionId}:${isWeb}:${profile}:${scopedCompanyId}

1.3 FLUJO DE ENTRADA (WEBHOOK)

  Endpoint: POST /whatsapp/webhook (WhatsAppController.receive, líneas 86-229)

  1. Verificación HMAC-SHA256 (verifyMetaSignature, líneas 344-367) contra WHATSAPP_APP_SECRET.
     Si falla → 401 INVALID_SIGNATURE.
  2. Respuesta 200 EVENT_RECEIVED inmediata (Meta requiere <5s).
  3. Parseo tipo de mensaje: text / interactive / location / button / audio / image / document.
  4. Dedupe por waMessageId: Map in-memory TTL 60s + PG advisory lock + whatsAppMessageLog DB.
  5. markRead fire-and-forget.
  6. Rate limit por teléfono (20 msg/60s) en phoneRateMap del controller.
  7. router.handleMessage(phone, type, payload, waMessageId).

  Verificación GET /whatsapp/webhook: Meta envía hub.mode=subscribe + hub.verify_token →
  se compara con WHATSAPP_VERIFY_TOKEN usando timingSafeEqual.

  Endpoints auxiliares:
  • POST /whatsapp/location-token        — protegido por INTERNAL_API_KEY (timingSafeEqual)
  • POST /whatsapp/save-location         — público, token one-time 30 min, JSONB atomic UPDATE
  • POST /whatsapp/save-location-by-slug — ídem por slug
  • GET  /whatsapp/daily-map-data?t=...  — token firmado con WHATSAPP_APP_SECRET, contiene cid
  • POST /whatsapp/live-location         — token firmado con uid, fid, role, name
  • GET  /whatsapp/live-locations?t=...  — consulta ubicaciones en vivo
  • POST /whatsapp/live-location/stop    — detiene GPS

1.4 GESTIÓN DE SESIÓN

  Tabla WhatsAppSession (prisma/schema.prisma):
  - TTL base: 30 min (AI) / 10 min (flow). Sliding window: cada mensaje renueva a 30 min.
  - flowState (JSON) contiene:
    · aiMessages            — historial Gemini format (MAX_HISTORY_MESSAGES=40)
    · selectedCompanyId / companyConfirmed — empresa scoped a nivel sesión
    · selectionContext      — contexto de pagination/numeric reply
    · pendingAiAction       — acción pendiente de confirmación (TTL 5 min)
    · pendingDocument       — foto/doc pendiente de adjuntar (TTL 30 min)
    · lastLocation          — última ubicación compartida
    · locationToken         — token del picker de ubicación
    · _pendingMessage / _pendingAction — congelados esperando selección de empresa
    · activeContext.lastFreightId/Code/Summary — contexto para LLM tras trimming

  Cleanup masivo cada 30 min (WhatsAppService.cleanupExpired):
  borra sesiones expiradas >2h, live locations, FreightTracking >90d, WA logs >90d,
  analytics >180d.

1.5 RESOLUCIÓN DE PERFIL (AiProfile)

  findUserByPhone (router líneas 3049-3094):
    1. Variante directa por user.phone (E.164 sin +, +598..., 0xx).
    2. Fallback: busca Company.phone → primer usuario activo ordenado por createdAt asc.
    3. Include: company + memberships(active=true) con sus companies.

  resolveAiProfile(user) (src/ai/core/ai-profile.ts:34-48):
    1. getActiveMembership → membership donde companyId === activeCompanyId.
    2. getCompanyType → si types[] incluye plant → plant; transporter → transporter; default producer.
    3. normalizeRole:
       - chofer/driver → driver
       - gerente/admin/platform_admin → manager
       - cualquier otro → operator
    4. Si role=driver && companyType=producer && autonomousDriverEnabled → autonomous_driver.
    5. Sino → ${companyType}_${role}.

  scopeUserToSessionCompany (src/common/user-company-scope.ts):
  Sobrescribe activeCompanyId/companyId/company con la membership correspondiente a
  session.flowState.selectedCompanyId. Usuarios multi-empresa reciben lista de selección
  hasta que companyConfirmed=true.

--------------------------------------------------------------------------------
2.1 PRODUCER_MANAGER
--------------------------------------------------------------------------------
  Tools:        list_freights, get_freight_detail, search_plants, search_fields,
                search_lots, create_freight_request, cancel_freight, confirm_action,
                attach_document
  Acciones:     Crear solicitudes de flete (origin/fieldId/lotId, destination/destPlantId/
                tolvinkPlantId, grain, weightKg, loadDate, loadTime, notes).
                Cancelar con motivo. Adjuntar docs. Buscar. Consultar fletes.
  Restricciones: No aprueba (planta). No asigna transportista. No asigna chofer/camión.
  Flujo especial: create_freight_request siempre entra a staging (stageAction) y retorna
                  pending_confirmation con botones [CONFIRMAR / CANCELAR].

--------------------------------------------------------------------------------
2.2 PRODUCER_OPERATOR
--------------------------------------------------------------------------------
  Tools:        list_freights, get_freight_detail, search_plants, search_fields,
                search_lots, create_freight_request, confirm_action, attach_document
  Diferencia:   NO tiene cancel_freight.

--------------------------------------------------------------------------------
2.3 PRODUCER_DRIVER (también aplica a TRANSPORTER_DRIVER y PLANT_DRIVER)
--------------------------------------------------------------------------------
  Tools:        list_freights, get_freight_detail, start_freight_trip,
                confirm_freight_loaded, confirm_freight_arrival, finish_freight,
                attach_document, confirm_action
  Acciones:     iniciar viaje → confirmar carga → confirmar llegada → finalizar.
                Adjuntar evidencia.
  Restricciones: NO crea fletes. NO cancela. NO asigna.
  Deterministic: "empece/salgo" → start_freight_trip
                 "cargue/ya cargue" → confirm_freight_loaded
                 "llegue" → confirm_freight_arrival
                 "termine/descargue" → finish_freight

--------------------------------------------------------------------------------
2.4 TRANSPORTER_MANAGER
--------------------------------------------------------------------------------
  Tools:        list_freights, get_freight_detail, accept_freight_assignment,
                reject_freight_assignment, assign_driver_and_truck,
                confirm_action, attach_document
  Acciones:     Aceptar asignación (auto-resuelve camión+chofer default si existen).
                Rechazar con motivo obligatorio. Asignar chofer+camión (fuzzy match).
  Restricciones: No aprueba (planta). No crea solicitudes. No inicia viaje ni
                 confirma carga/entrega (eso es del driver).
  Flujo especial: accept con defaults ya asignados → devuelve already_accepted.
                  assign_driver_and_truck requiere staging.

--------------------------------------------------------------------------------
2.5 PLANT_MANAGER
--------------------------------------------------------------------------------
  Tools:        list_freights, get_freight_detail, approve_freight_request,
                assign_transport_company, cancel_freight, confirm_action,
                attach_document
  Acciones:     Aprobar fletes de productor. Asignar transportista (fuzzy match vía
                resolveTransportCompany). Cancelar.
  Restricciones: No opera como transportista (salvo own-fleet a nivel freights.service).

--------------------------------------------------------------------------------
2.6 PLANT_OPERATOR
--------------------------------------------------------------------------------
  Tools:        Igual a plant_manager PERO SIN cancel_freight.

--------------------------------------------------------------------------------
2.7 PLANT_DRIVER
--------------------------------------------------------------------------------
  Tools:        Idéntico a producer_driver / transporter_driver.

--------------------------------------------------------------------------------
2.8 AUTONOMOUS_DRIVER
--------------------------------------------------------------------------------
  Tools:        list_freights, get_freight_detail, get_dashboard, search_plants,
                search_fields, search_lots, prepare_autonomous_freight, confirm_action,
                finish_autonomous_freight, cancel_freight, attach_document
  Requisito:    company.type=producer + role=chofer + company.autonomousDriverEnabled=true
  Flujo especial:
    prepare_autonomous_freight (tool-executor.ts líneas 491-547):
    - Con flete activo propio → stage finish_and_create con botón único FINALIZAR.
    - Sin flete activo → autoDetectTruck (assignedUserId=user.id primero, fallback al
      primer camión de company) → stage prepare_autonomous_freight.
    - Flete se crea en estado loaded (createAutonomousFreight en freights.service.ts:567).
    finish_autonomous_freight: register_plant_arrival marca arrivedAtPlantAt sin finalizar.
    Menú autónomo (showMainMenu):
    - Con arrivedAtPlantAt → botón FINALIZAR FLETE.
    - Sin arrivedAtPlantAt + flete activo → botón CONFIRMAR LLEGADA.
    - Sin flete activo → botón SOLICITAR FLETE.

SECCIÓN 4: GAPS Y RIESGOS
================================================================================

--------------------------------------------------------------------------------
4.1 VALIDACIONES DE ROL DÉBILES O AUSENTES
--------------------------------------------------------------------------------

  GAP-001: handleListReply — dispatcher genérico (router líneas 1265-1269)
    Los listIds se inyectan de vuelta al AI como "[Seleccionó: <title> (id: <safeId>)]".
    El sanitizado /[^\w\-.:]/g limita pero no previene prompt injection via título.
    El title se trunca a 50 chars pero corchetes dentro no se escapan.
    RIESGO: bajo pero no nulo en título de empresa/camión con contenido malicioso.

  GAP-002: handleGetFreightDetail en path AI vs path directo
    tool-executor:handleGetFreightDetail filtra por participantCompanyIds pero sin
    chequeo de rol en empresa activa. showFreightDetail (router) SÍ tiene hasAccess
    check. Inconsistencia: un operator de planta puede ver detalles via AI que no
    debería via UI directa.

  GAP-003: daily-map-data token permanente
    Token firmado con cid no tiene TTL. Un token válido da acceso indefinido a
    freights de esa company aunque el usuario sea desactivado.

  GAP-004: findUserByPhone fallback por Company.phone
    Si un teléfono está mal configurado en varias empresas, agarra el PRIMER usuario
    activo (createdAt asc). Posible impersonación si telefono mal asignado.

  GAP-005: saveLocationToActiveFreights para no-drivers
    Graba GPS en TODOS los fletes activos donde cualquier companyId del user es
    origin/dest/transporter. Un operario de productor puede aparecer como tracker
    en fletes donde no debería.

  GAP-006: Sin validación de user.active en onLocationSaved
    Un usuario desactivado con sesión activa puede seguir enviando ubicaciones
    hasta que la sesión expire.

--------------------------------------------------------------------------------
4.2 FLUJOS SIN MANEJO DE ERROR ROBUSTO
--------------------------------------------------------------------------------

  GAP-007: onLocationSaved sin Sentry
    Si handleAiChat lanza dentro de onLocationSaved, el phone lock se libera
    por el finally pero el error no es capturado ni reportado.

  GAP-008: handleButtonReply 'confirm' legacy sin try/catch
    JSON.parse(result || '{}') (router línea 1140-1179) sin try/catch.
    Si confirmPendingAction devuelve string no-JSON → throw no capturado.

  GAP-009: Crons desactivados
    checkStaleFreights y checkDailySummary comentados en whatsapp.service.ts (líneas 63-69).
    Si se reactivan sin feature flag, checkDailySummary usa take:500 con N+1 queries
    y puede throttlear la Meta API con >500 usuarios.

  GAP-010: downloadMedia presupuesto de tiempo
    Si primer fetch tarda exactamente 10s, segundo fetch no tiene presupuesto suficiente.

  GAP-011: audit_log fire-and-forget
    auditLog en handleCompanySelection es fire-and-forget (.catch(warn)).
    Si falla, se pierde el audit trail silenciosamente.

--------------------------------------------------------------------------------
4.3 POSIBLES FILTRACIONES DE DATOS ENTRE EMPRESAS
--------------------------------------------------------------------------------

  GAP-012: resolveAllCompanyIds sin activeCompanyId devuelve TODO
    Si user.activeCompanyId no está seteado (posible en path web), devuelve IDs de
    TODAS las memberships. Afecta: list_freights, get_dashboard, search_fields,
    search_lots. En WhatsApp siempre hay activeCompanyId, pero en endpoints web
    compartidos podría no haberlo.

  GAP-013: pendingDocument.companyId mismatch race window
    El check existe pero ocurre solo cuando se procesa el siguiente mensaje.
    Si el usuario adjunta antes de que se detecte el mismatch, puede haber una
    ventana donde el documento se asigna a la empresa incorrecta.

  GAP-014: activeContext tras primera selección de empresa
    stripOperationalFlowState solo borra el activeContext si companyChanged=true.
    La primera selección (null → A) no considera esto "cambio". Validar que
    no queden datos de empresa anterior en contexto.

  GAP-015: Signed tokens con mismo secreto
    verifySignedToken y verifyMetaSignature comparten WHATSAPP_APP_SECRET.
    Un token filtrado podría usarse indistintamente (anti-patrón, separar secrets).

4.4 ESTADO IN-MEMORY EN INSTANCIA ÚNICA

  Las siguientes estructuras NO están en Redis y se pierden en restarts/scale-out:
  • phoneLocks (Map)
  • gpsWriteCooldowns (Map)

  • messageRate (Map, controller)

  requiere migración de todo esto a Redis antes de añadir instancias.
